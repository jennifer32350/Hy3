# Hy3 Data Analyst MCP v0.2 产品需求文档（PRD）

> 文档状态：开发输入稿
> 目标版本：v0.2
> 适用对象：产品负责人、Python/MCP 工程师、测试工程师、执行开发任务的 AI Agent
> 配套文档：[v0.2 技术规格](technical-spec-v0.2-cn.md)、[v0.2 开发计划](development-plan-v0.2-cn.md)

## 1. 文档目的

本文定义 Hy3 Data Analyst MCP v0.2 必须解决的产品问题、用户场景、功能范围、优先级和
验收标准。执行开发的工程师或 AI Agent 不得只根据功能名称自行扩展范围；涉及数据结构、
安全限制、失败行为和测试方式的实现，必须同时遵守配套技术规格。

## 2. 产品一句话定义

Hy3 Data Analyst MCP 是一个本地 stdio MCP Server：它在受限目录中安全读取结构化数据，
由 Hy3 理解复杂分析意图并规划步骤，由本地确定性执行器计算事实，最后返回可追溯的分析
报告和可展示图表。

它不是通用自主 Agent、聊天客户端、任意代码解释器或数据库系统。Cursor、CodeBuddy 等
MCP 客户端负责对话和工具调度，本项目负责安全且可信的数据分析能力。

## 3. 当前产品痛点

### P-01：复杂问题被压缩成一次简单计算

当前一个问题只能生成一个 `AnalysisPlan` 并执行一种操作。例如用户提出：

> 比较各区域销售额和利润，找出异常记录，解释异常对区域排名的影响，并提出建议。

当前系统只能选择分组聚合、Top-K 或 IQR 异常检测中的一种，无法在同一次调用中完成完整
分析链。这会导致结论片面，也迫使用户自己拆解问题。

### P-02：分析操作覆盖不足

当前只支持描述统计、单一分组聚合、Top-K、Pearson 相关、月度趋势、缺失值和 IQR 异常。
用户常用的安全筛选、多指标聚合、频数占比、分布、期间对比、交叉表和派生指标尚不支持。

### P-03：数据处理口径不透明

当前能够发现缺失值和重复行，但分析结果没有统一说明：

- 是否排除了缺失行；
- 是否保留了重复记录；
- 日期或数值转换失败了多少行；
- 计算实际使用了多少行；
- 分母和时间粒度是什么。

用户可能看到正确的数值，却无法判断数值是如何得到的。

### P-04：结论与证据的对应关系太弱

当前只有一组 Evidence 和自由文本解释。复杂报告无法明确指出每条发现来自哪个步骤、哪条
记录或哪个指标，也没有统一 Evidence ID。这不利于核验和发现模型幻觉。

### P-05：输出更像调试 JSON，而不是分析报告

当前输出包含 plan、evidence、conclusion 等底层字段，但缺少稳定的业务阅读结构，例如：

- 执行摘要；
- 关键发现；
- 异常及影响；
- 建议；
- 数据口径；
- 风险与限制。

用户需要自己阅读 JSON 才能理解分析价值。

### P-06：图表停留在文字建议

当前 `suggest_visualization` 只返回图表类型和字段建议，不生成真实图表。用户无法直观看到
效果，也难以完成演示和交付。

### P-07：缺少可量化的效果评测

当前测试重点验证代码正确性和安全边界，但没有覆盖足够多的真实业务问题。项目无法回答：

- 升级后到底比 v0.1 强多少；
- 哪类问题仍然失败；
- 数值正确率和证据引用率是多少；
- Hy3 规划失败时系统是否稳定降级。

## 4. 目标用户

### 4.1 主要用户

- 在 Cursor、CodeBuddy 等客户端中分析本地 CSV/JSON/JSONL 的学生、研究人员和开发者。
- 希望用自然语言完成探索性分析，但不希望模型执行任意代码的用户。
- 需要在演示、报告或 PR 中展示可复核分析结果的开源项目贡献者。

### 4.2 用户前提

- 用户能够配置 `HY3_DATA_DIR` 和 TokenHub/自部署 Hy3 API。
- 用户知道待分析文件的名称，但不要求知道字段的精确类型。
- 用户可能提出模糊或复合问题，系统应在安全范围内完成合理拆解或返回明确限制。

## 5. v0.2 产品目标

### G-01：一次调用完成复合分析

单次 `analyze_dataset` 最多规划并执行 6 个有序白名单步骤，支持筛选、计算、比较、异常检测
和解释的组合。

### G-02：所有重要结论均可追溯

每个计算步骤产生稳定 Evidence ID。每条事实性 Finding 必须引用至少一个有效 Evidence ID，
数值性结论不得脱离确定性 Evidence。

### G-03：数据口径明确且无静默处理

缺失值、重复记录、类型转换、除零、无效日期和结果截断必须按照显式策略处理，并在输出中
记录。系统不得静默丢弃数据或修改原始文件。

### G-04：输出可直接阅读和展示

默认返回结构化业务报告，而不是仅返回底层执行结果；同时保留详细计划和 Evidence，便于
调试、复核和客户端展示。

### G-05：生成真实图表

能够根据已验证数据生成受限 PNG 图表。图表数据必须来自本地确定性计算，不允许 Hy3 提供
或篡改绘图数值。

### G-06：效果可量化

建立至少 30 个真实问题的评测集，能够对比 v0.1 与 v0.2 的端到端完成率、计划有效率、
数值正确率和证据引用率。

## 6. 非目标

v0.2 明确不做以下功能：

- 通用聊天 UI、Web UI 或独立桌面客户端；
- 数据库、远程 URL、云存储连接器；
- Excel、Parquet 和多文件 Join；
- 自动机器学习、预测、因果推断和模型训练；
- 任意 Python、Shell、SQL、正则表达式或 Pandas 表达式执行；
- 模型生成代码后执行；
- 修改或覆盖用户原始数据文件；
- 持久化用户会话、隐式记忆或后台任务系统；
- 无限制步骤、自主循环或无限模型重试；
- 依赖 LangChain、LlamaIndex 等通用 Agent 框架。

这些能力如有需要，应另行进入 v0.3 或后续版本评审，不得在 v0.2 开发过程中顺手加入。

## 7. 核心用户场景

### S-01：综合经营分析

用户问题：

> 比较不同区域的收入、成本和利润，给出利润率，找出表现最好和最差的区域，并说明异常值
> 是否改变了排名。

期望行为：

1. 检查关键字段和数据质量；
2. 计算区域收入、成本、利润和受限派生指标利润率；
3. 检测利润异常；
4. 比较包含和排除异常记录时的排名；
5. 返回带 Evidence 引用的结论、限制和建议。

### S-02：时间变化分析

用户问题：

> 对比最近两个季度的销售额和订单量，找出增长最快的类别，并说明变化是否可能受缺失值影响。

期望行为：

1. 验证日期字段并声明季度口径；
2. 计算两个期间的汇总值和变化率；
3. 按类别比较；
4. 报告缺失日期或目标值造成的影响；
5. 输出趋势图或分组柱状图。

### S-03：数据质量诊断

用户问题：

> 检查这个文件是否适合用于销售分析，重点关注重复记录、缺失字段、异常利润和类型问题。

期望行为：

1. 返回质量概览和严重程度；
2. 定位问题字段及受影响行数；
3. 不自动修改原始文件；
4. 给出明确的处理建议和分析风险。

### S-04：类别结构和占比

用户问题：

> 各产品类别贡献了多少收入和利润，占比分别是多少？是否过度集中在单一类别？

期望行为：

1. 多指标分组聚合；
2. 计算类别占比；
3. 返回排序、集中度事实和限制；
4. 输出适合展示结构差异的图表。

### S-05：安全失败

用户问题超出能力：

> 训练一个预测下月销售额的模型，并运行模型生成的 Python 代码。

期望行为：

- 明确说明 v0.2 不支持预测训练和代码执行；
- 不生成或执行代码；
- 建议用户改为查看历史趋势、期间对比或相关性。

## 8. 功能需求

### FR-001：增强数据检查

`inspect_dataset` 必须保持原有参数和返回字段兼容，并新增：

- 数据质量摘要；
- 问题严重程度（info/warning/error）；
- 数值/日期转换风险；
- 常量列、高基数类别列和疑似 ID 列提示；
- 重复行和缺失值对分析的潜在影响；
- 明确说明检查没有修改原始文件。

### FR-100：多步骤分析计划

- `analyze_dataset` 必须支持 1～6 个按顺序执行的步骤。
- 每个步骤必须具有唯一 ID、白名单操作、输入引用、结构化参数和目的。
- 输入只能引用原始数据或此前步骤，不允许前向引用和循环依赖。
- 计划无效时最多允许 Hy3 修复一次；再次失败必须安全返回错误。
- 不允许为了完成问题生成任意代码或未注册操作。

### FR-110：分析操作

必须保留现有 7 类操作，并在 v0.2-alpha 至少新增：

- 安全筛选 `filter_rows`；
- 多指标聚合 `multi_aggregate`；
- 类别频数和占比 `value_counts`；
- 期间对比和变化率 `period_compare`。

v0.2 正式版还应支持：

- 分布和分位数 `distribution`；
- 受限交叉表 `pivot_table`；
- 受限派生指标 `derived_metric`。

所有操作语义、限制和失败条件以技术规格为准。

### FR-120：显式数据质量策略

- 默认保留原始数据并产生警告，不得静默去重或删除缺失行。
- 分析步骤可以声明受限的缺失值、重复值和类型转换策略。
- 任何排除必须记录处理前行数、处理后行数、排除行数和原因。
- 原始 DataFrame 和原始文件不得被就地修改。
- 无效日期、非数值内容、无穷值和除零必须返回稳定警告或错误。

### FR-130：Evidence Ledger

- 每个成功计算步骤必须产生 Evidence ID。
- Evidence 必须包含来源步骤、操作、摘要、指标、有限记录、处理行数、截断状态和警告。
- 内部计算可以使用完整的受限 DataFrame，但发送给 Hy3 的 Evidence 必须有界。
- 默认每步最多序列化 100 条记录，整个工作流最多序列化 300 条记录。
- Evidence 不得包含 API Key、绝对个人路径或完整原始数据集。

### FR-140：可信分析报告

默认报告必须包含：

- `executive_summary`；
- `findings`；
- `anomalies`；
- `recommendations`；
- `data_scope`；
- `limitations`；
- `warnings`；
- `suggested_follow_ups`；
- `plan` 和 `evidence`。

其中：

- 事实性 Finding 必须至少引用一个 Evidence ID；
- 解释和建议必须与事实明确区分；
- 相关性不得描述为因果关系；
- 样本不足、严重缺失或结果截断时不得输出高置信度结论；
- 用户可以选择 `concise` 或 `detailed` 输出模式。

### FR-200：可视化建议

`suggest_visualization` 必须保持兼容，并增强为：

- 图表建议引用 Evidence 或确定性聚合数据；
- 标题、字段、聚合、排序和 Top-N 均通过 Schema 校验；
- 只能使用真实列名和允许的图表类型；
- 不允许 Hy3 提供图表中的数值；
- 返回图表适用场景、数据口径和局限。

### FR-210：图表渲染

新增 `render_visualization` MCP 工具：

- 支持 bar、line、scatter、histogram、box；
- 使用本地确定性数据和无界面渲染后端生成 PNG；
- 返回图表元数据、Evidence 引用和 MCP 图像内容；
- 输出仅能写入配置的受限目录；
- 不允许覆盖原始数据或任意现有文件；
- 单次最多生成 3 张图，单图大小和像素尺寸必须受限。

### FR-300：兼容性

- 原有三个工具名称不得改变。
- 现有必填参数不得删除或改名。
- 现有调用在不提供新参数时必须继续工作。
- 原有返回字段保留；新增报告字段采用向后兼容的扩展方式。
- Python 3.10～3.13、Windows 和 Ubuntu 必须通过 CI。

### FR-310：可观测性

- 返回总耗时和各步骤耗时，但不得返回密钥或完整请求体。
- stdio Server 的 stdout 只能用于 MCP 协议。
- 日志只能写入 stderr，并且默认不记录数据样例和 Hy3 完整响应。
- 错误必须使用稳定的 `error/message/hint` 结构，并指出失败步骤。

## 9. 用户可见输出要求

默认 `analyze_dataset` 输出应遵循以下阅读顺序：

1. 一段不超过 600 字的执行摘要；
2. 3～8 条按重要性排序的关键发现；
3. 异常和数据质量风险；
4. 基于证据的建议；
5. 数据范围与处理口径；
6. 限制和警告；
7. 可继续追问的问题；
8. 详细计划和 Evidence。

语言默认跟随用户问题语言。字段名和 Evidence ID 保持原样，不翻译或改写。

## 10. 质量指标

### 10.1 离线确定性指标

- 数值正确率：100%。
- 路径、Schema、步骤依赖和操作参数校验测试通过率：100%。
- 原始文件被修改次数：0。
- 模型生成内容触发动态执行次数：0。

### 10.2 真实任务指标

- 至少 30 个评测问题。
- 核心评测端到端成功率不低于 85%。
- 有效计划生成率不低于 90%（包含一次修复后的结果）。
- 数值性 Finding 的有效 Evidence 引用率：100%。
- 支持范围内复合问题无需用户手工拆分的比例不低于 80%。

### 10.3 工程指标

- Ruff、Mypy、Pytest 和 `git diff --check` 全部通过。
- 项目总覆盖率不低于 85%。
- 新增工作流校验器、执行器和安全渲染器必须覆盖主要分支和失败路径。
- Windows/Ubuntu、Python 3.10/3.12 CI 全部通过。

## 11. 发布验收场景

v0.2 发布前必须在示例销售数据上完成以下演示：

1. 一次调用完成区域收入/利润对比、利润率、异常检测和排名影响分析。
2. 输出中正确发现缺失记录、重复记录和 `profit=-900` 的异常。
3. 每条数值性发现均能定位到 Evidence ID。
4. 能生成至少一张真实 PNG 图表，且图中数值与 Evidence 一致。
5. Cursor 和 CodeBuddy 均能发现并调用所有公开工具。
6. 错误 API Key、无效路径、越界步骤、虚构列名和非法派生指标均安全失败。
7. 演示、日志、截图和提交文件中不出现真实 API Key 或个人绝对路径。

## 12. 冻结决策

以下决策在 v0.2 开发期间视为冻结，不应由开发工程师或 AI Agent自行更改：

1. Hy3 只负责规划和解释，最终数值由本地确定性执行器产生。
2. 不执行任何模型生成代码或字符串表达式。
3. 工作流最多 6 步，计划最多修复一次。
4. 默认不删除或修改数据；所有处理必须显式记录。
5. 图表数据只能来自确定性计算。
6. 保持原有三个 MCP 工具兼容；图表渲染以新增工具提供。
7. Server 不维护隐式对话状态；每次调用必须包含完成任务所需的信息。
8. v0.2 不加入多文件 Join、数据库、预测训练和通用 Agent 框架。
